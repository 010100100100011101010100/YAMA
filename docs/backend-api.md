# Local API contract

All report endpoints run in Next.js's Node runtime. They require a Better Auth session and return `Cache-Control: private, no-store`. Mutations require the configured exact `Origin`. Report/review JSON bodies are capped at 128 KiB; evidence uploads use bounded raw bytes with matching extension/MIME/signatures: text/plain up to 64 KiB, PDF/PNG/JPEG up to 5 MiB. Reports are synthetic-only at this stage. No request may supply an owner ID.

Start a demo session with `POST /api/auth/sign-in/anonymous`, JSON `{}` and the configured Origin. Retain the HTTP-only session cookie in the client. `POST /api/auth/sign-out` ends that session. This is demo authentication, not identity verification. [Anonymous plugin](https://better-auth.com/docs/plugins/anonymous), [MongoDB adapter](https://better-auth.com/docs/adapters/mongo)

| Method | Path | Contract |
| --- | --- | --- |
| GET | `/api/health` | Generic database readiness, no credentials/query errors |
| GET | `/api/reports` | Most recent 50 owned report summaries |
| POST | `/api/reports` | Create/replay; UUID `Idempotency-Key` header required |
| GET | `/api/reports/:id` | Owned report, original messages, current assertions and revision |
| PATCH | `/api/reports/:id` | One typed revision operation; invalidates confirmation |
| POST | `/api/reports/:id/confirm` | Explicit current-revision acknowledgement; queues graph work atomically |
| GET | `/api/reports/:id/connections` | 202 pending or 200 ready; current confirmation/projection; source-linked explanation, recipe version and fixed linkage limit |
| GET | `/api/reports/:id/dialogue` | Owned foreground role, preferences, assistant history and current turn |
| POST | `/api/reports/:id/dialogue` | Version/revision-bound reply, delivery acknowledgement, role/language/preference or stop command |

Create:

```json
{
  "synthetic": true,
  "language": "hinglish",
  "narrative": "Fictional example: maine phone order kiya, delivery nahi hui."
}
```

Language is `en`, `hi`, or `hinglish`. Narrative/message/assertion values are 1–6000 characters; original script and whitespace are preserved. A report holds at most 50 messages and 100 assertions. IDs are UUIDs generated by the server.

Each PATCH uses `expectedRevision` and one operation:

```json
{ "operation": "add_message", "expectedRevision": 1, "text": "Fictional correction: the seller replied later." }
```

```json
{
  "operation": "propose_assertions",
  "expectedRevision": 2,
  "proposals": [
    {
      "field": "pattern",
      "value": "paid",
      "polarity": "affirmed",
      "source": { "messageId": "SERVER_MESSAGE_UUID", "start": 0, "end": 20 }
    }
  ]
}
```

Proposal fields: `narrative`, `amount`, `item`, `date`, `pattern`, `note`. Pattern values currently allowed: `paid`, `promised_delivery`, `not_delivered`, `no_reply`. Source ranges must refer to an owned report's message and stay inside it. They use UTF-16 offsets. Proposals are labelled client proposals, not model or independently verified facts. At most 20 proposals per request.

```json
{
  "operation": "correct_assertion",
  "expectedRevision": 3,
  "assertionId": "SERVER_ASSERTION_UUID",
  "value": "Corrected value",
  "included": true,
  "polarity": "uncertain"
}
```

At least one of value/included/polarity is required. The original value/source cannot be overwritten. Confirm separately:

```json
{ "expectedRevision": 4, "acknowledged": true }
```

Confirmation repeats safely for that revision. A later edit requires confirmation again. Graph work is asynchronous; run `worker:graph` for pending projections. A ready response contains only published synthetic catalogue candidates, shared/differing pattern tags, relevant item differences, and `linkage.status: "not_assessed"`. It does not disclose other accounts' reports or claim a common perpetrator.

Errors have shape `{ "error": { "code": "revision_conflict" } }`; no raw driver errors or report text are returned in error messages. Main statuses: 400 invalid payload/ID/key/source; 401 no session; 403 rejected origin; 404 missing or unowned report; 409 stale revision/idempotency conflict/confirmation required; 413 oversized body; 415 wrong media type; 422 report limits/nothing to confirm; 429 account rate limit; 503 database/projection unavailable. Pending graph results return 202 with `status: "pending"`.

Owned evidence upload/list/extraction/source/review/archive endpoints inherit the [plain-text foundation](evidence-service.md). PDF/image extraction returns HTTP 202 when queued/processing, uses a durable isolated worker and adds an owned cancellation endpoint. Document review requires the displayed byte hash and `textSha256`, acknowledgement and current revision. [Document contract and limits](document-evidence.md). Reviewed file messages expose `evidenceSource` (file ID, original name, byte SHA-256 and optional frozen extraction receipt with image ID/text hash/page ranges); their initial note assertion has origin `evidence` and remains `not_verified`. File text cannot set structured pattern tags or confirmation automatically.

Saathi extraction uses owned durable receipts under `/api/reports/:id/agent-tasks`: enqueue/history/read/cancel and explicit acceptance. Acceptance supplies the current base revision, acknowledgement, preview hash and selected stored IDs; it cannot supply proposal content or agent/provider identity. It atomically creates an unconfirmed draft revision and accepted receipt. Accepted assertions expose `origin: agent_proposal` and trusted `agentSource` metadata, while retaining `verification: not_verified`. See [complete proposal and worker contract](agent-proposal-review.md).

Text dialogue uses one Mongo conversation per report. Every command includes `expectedRevision` and `expectedVersion`. A `reply` also supplies a UUID request key, the last saved message UUID, registered agent, language and automatic-handoff preference. Replies are separate from report assertions. A `delivered` acknowledgement supplies the current ready turn UUID; it persists the reply and queues a validated handoff atomically, with at most three replies per chain. `select`, `language`, `automatic` and `stop` commands revoke pending output. Generated text cannot confirm or write report details. See [dialogue contract, limits and provider setup](text-dialogue.md).

There are no payment, model-provider, raw-query, public-report publication, permanent deletion or official complaint-submission endpoints in this increment.


## Assistance and private action review — increment 5

`GET /api/assistance?language=en|hi|hinglish` is public and takes no report or private query. It returns fixed dated India options; outdated contacts are withheld. `GET /api/reports/:id/actions` requires the owned session and returns a deterministic summary/active-file inventory with content receipt. `POST` to that same private route requires exact Origin and exactly `expectedRevision`, `receipt`, and `acknowledged: true`. A current transaction saves an immutable private review; identical retries return its original timestamp. Changed report, confirmation or file metadata require a new review. No confirmation, graph projection, filing, sending or charge occurs. [Schemas, official sources, lifecycle and limits](assistance-actions.md).

## Increment 7: public lookup

Authenticated, revision-bound public search/page jobs and cancellation routes are documented in [public-web.md](public-web.md). Inputs contain predefined topics or owned source references, never arbitrary queries/URLs. Fixtures are the default, results are untrusted, and report/graph state cannot be changed by these tools.

## Increment 9: approved notifications

Owned workspace-link previews, application approval, history and cancellation routes are documented in [notifications.md](notifications.md). Operator-registered synthetic destinations, exact content receipts and explicit fallback consent are required for live attempts. Fixture capture is the default. Acceptance is not confirmed inbox delivery; uncertain dispatches are never automatically replayed.

## Billing and detail entitlements (2026-10-14)

The [billing contract](billing.md#http-contracts) adds fixed test checkout, owned balance/status, a raw-body signed webhook, and confirmed-report fixture preview/read/unlock endpoints. Payment grants require worker verification; return parameters cannot grant. Existing Connections, report/evidence access and essential assistance remain free. No browser checkout controls or actual advanced-analysis generator are part of this increment.

## Saved-chat status (2026-10-14)

`GET /api/reports` includes owned bounded chat titles, `resolution` and `statusVersion` for the latest fifty reports. `GET /api/reports/:id/chat-status` returns `{status: {reportId, resolution, version}}`. `PATCH` accepts strict `{resolution: "unresolved"|"resolved", expectedVersion}`; same target replays are idempotent, conflicting versions return 409, and foreign accounts return 404. Status updates do not alter incident revision/confirmation. Existing auth, origin and no-store boundaries apply. Delivered dialogue messages optionally preserve the validated `handoff` target/reason for group-chat display.
