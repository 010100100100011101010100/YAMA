# Runtime providers and useful service functions

Researched 2026-10-07 against official documentation and pricing. These are planning decisions and candidates, not connected services. Account eligibility, regional availability, taxes, and actual credits need checking before activation. No new accounts, subscriptions, API keys, provider calls, or SDK installations were made for this research.

## Confirmed direction

- **Speech:** Sarvam transcription and synthesis, retaining the selected `saaras:v4` and `bulbul:v3` Model APIs. Three consistent identities: two female voices and one male voice. Which agent receives which speaker remains unassigned until auditioning.
- **Text intelligence:** OpenAI for dialogue, structured extraction, and explanations across all three agents. This replaces the earlier Sarvam text-model selection. Exact OpenAI model IDs and snapshots remain to be selected using latency, tool-use, cost, Hindi, and Hinglish fixtures.
- **Language choices:** English, Hindi, and Hinglish in both text and voice. More Indian languages follow later. Preserve the user's original wording and script. Hinglish is an application preference for code-mixed Hindi/English, not an invented Sarvam language code. Test Roman Hindi and mixed Devanagari/English; do not silently translate the original account.
- **Databases (updated 2026-10-08):** MongoDB owns reports, assertions, original messages, immutable revisions, Better Auth sessions and durable graph jobs. FalkorDB holds rebuildable confirmed-report graphs and a separate authored synthetic catalogue for connection discovery. This supersedes the earlier FalkorDB-primary/PostgreSQL note. Evidence binaries will use private file/object storage. See `backend-architecture.md` for the implemented foundation.
- **Public web:** Exa and Firecrawl adapters are implemented through owned jobs and the specialist dispatcher. Exa uses predefined public topics; Yama fetches and sanitizes a selected approved page before Firecrawl HTML parsing. Fixtures remain the default, live account checks await keys, and autonomous chat browsing is not enabled. See [the implemented contract](public-web.md).
- **Monitoring:** Langfuse is selected, but not connected. Trace agent turns, handoffs, tool status, latency, model/version, usage, and evaluation outcomes. Minimize and redact telemetry before export.
- **Mail:** Resend is primary; Nodemailer through the future Yama Gmail account is the fallback. The [notification outbox](notifications.md) is implemented with explicit approval, controlled synthetic recipients and capture-only fixtures. Sending-domain setup, credentials and live verification remain pending. Agents can prepare the fixed preview; actual dispatch is a trusted application action.
- **Future partnership stage:** DigiLocker is deferred, potentially supporting optional identity verification or consented document import in a police complaint workflow. Complaint submission would use a separate approved channel. It is not an initial-demo requirement, an approved login provider, or a connected service. Better Auth remains the account/session layer.

Sarvam documents female `priya` and `ishita`, and male `shubh` and `ratan` among its recommended Hindi/English candidates. Audition them across the same English, Hindi, and Hinglish phrases before choosing three voices; these are candidates, not assignments. Code-mixed input is supported, while the API's language codes include `en-IN` and `hi-IN`. [Speaker catalogue](https://docs.sarvam.ai/api/api-guides-tutorials/text-to-speech/how-to/change-the-speaker-voice), [TTS request contract](https://docs.sarvam.ai/api-reference/text-to-speech/convert)

Use the official OpenAI Python/TypeScript SDK for streamed dialogue and function calls, with schema-constrained extraction and application validation. The existing coordinator still owns speaking turns, handoffs, role permissions, and revision checks; a model's tool request is not permission to execute it. [Function calling](https://developers.openai.com/api/docs/guides/function-calling), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

## DigiLocker: deferred to a future partnership stage

The user deferred DigiLocker on 2026-10-07 and suggested a future complaint-filing workflow if Yama partners with police. Plan consented identity/document access as one part of that workflow; do not assume DigiLocker supplies a police complaint-submission API. A future official partnership must define the separate submission channel, supported jurisdiction, destination, required fields/documents, receipt/status contract, and permitted data handling. The user reviews the final complaint package and explicitly authorizes submission. Display a submitted/registered status only when the official channel supplies the corresponding acknowledgement; generating a draft or sending email does not establish that status.

The official onboarding FAQ directs DigiLocker integrations/requesters to API Setu registration and requires authorized scopes, a registered redirect URI, and OAuth authorization. Some FAQ entries concern **Entity Locker**, which is for organizations; do not use those as personal DigiLocker contracts. Obtain the current specification and approval for Yama's precise use case rather than implementing from an old public PDF. Partner eligibility, fees, permitted document types, test access, and any federated sign-in entitlement remain unverified. [Official onboarding FAQ](https://www.digilocker.gov.in/assets/FAQ%20DL%20EL_onboarding.pdf)

Recommended product design: retain Better Auth login; offer **Connect DigiLocker** only when the user wants to verify an identity claim or import a relevant issued document. Use the approved authorization flow with state, PKCE where required/supported, server-side token handling, minimum scopes, document selection, and a clear purpose. The user sees an import preview before it becomes report evidence. Do not collect Aadhaar numbers in chat, retrieve all documents automatically, or expose tokens/documents to generic agent tools. Identity/document authenticity does not verify that an incident happened. Issued documents and user-uploaded files require separate provenance and verification labels.

If the partner approval also permits federated sign-in, assess an explicit account-linking adapter later. Do not silently replace account sessions, merge users by display name/email, or require DigiLocker to access narration and essential help. No DigiLocker integration or consent/import fixture work is required for the initial demo.

## Mail and monitoring design

Resend requires a sending domain Yama controls and verifies; `gmail.com` cannot be verified by Yama. Use a future verified domain address for `From`, and the Yama Gmail as `Reply-To` if desired. Nodemailer authenticates separately to Gmail for fallback sends, using OAuth2 preferably or an eligible app password with two-step verification. Gmail quotas and anti-abuse restrictions make this a bounded fallback, not a promised replacement at scale. The Gmail account is not yet created/connected here. [Resend domains](https://resend.com/docs/dashboard/domains/introduction), [send API](https://resend.com/docs/api-reference/emails/send-email), [Nodemailer OAuth2](https://nodemailer.com/smtp/oauth2), [Google app passwords](https://support.google.com/accounts/answer/185833), [Gmail limits](https://support.google.com/mail/answer/22839?hl=en)

The implemented synthetic outbox uses a logical message ID, fixed template, operator-confirmed test recipient, expiry and bounded provider attempts. Production account-email verification remains separate. Resend supports idempotency keys for 24 hours, but Gmail does not share that deduplication state. An ambiguous timeout must become **delivery unknown**, not an immediate second-provider send. Retry/reconcile with the original provider first; only fail over when non-acceptance is established. Rejected recipients and policy/bounce failures must not be bypassed through fallback. A consistent `Message-ID` alone does not guarantee deduplication. [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys)

Langfuse should show Saathi/Drishti/Disha spans beneath a shared conversation trace: speaking-turn changes, background tasks, retries, stale-result rejection, tool duration, model/version, and usage. Keep prompts, transcripts, identities, evidence, document contents, and access tokens out of hosted traces. Test attribute allowlists/redaction before enabling automatic model/SDK instrumentation. Langfuse documents pre-export masking; the legacy Python `mask` hook does not cover final raw spans from third-party instrumentation. [Masking guidance](https://langfuse.com/docs/observability/features/masking)

For the synthetic demo, evaluate Cloud Hobby instead of running the full self-hosted stack alongside everything else. Langfuse's VM deployment guidance recommends at least four cores and 16 GiB memory; that is not a hard minimum for every tiny local experiment, but it exceeds this laptop's RAM. India-hosted observability for real reports remains a deployment decision under the existing data policy. [Deployment guidance](https://langfuse.com/self-hosting/deployment/docker-compose)

See [agent-tool-catalogue.md](agent-tool-catalogue.md) for proposed callable functions and the review/export UX. None of those new adapters has been enabled in the role capability registry.

## How agent-created web requests should work

Keep web tools behind Yama's server-side function dispatcher and SDK/REST adapters. A Codex design MCP is not a production agent connection.

1. Look up authorized Yama records or a curated, dated guidance entry. If a task requires freshness or the user asks for a public source, the agent can propose a web request. An empty case result alone must not trigger a broad search for a private person.
2. Use distinct proposed tool contracts: `search_public_web(query, purpose, domains)` to discover sources and `fetch_public_page(url, purpose)` to read one. These names are not yet registered callable tools in `agents/capabilities.json`.
3. The dispatcher validates the role and current generation, approved purpose, domain policy, query privacy, and remaining budget. Never send the incident transcript, report IDs, private identifiers, or evidence links as search context. Never fetch internal/local addresses, cloud metadata endpoints, authenticated pages, or private file URLs; recheck redirects and DNS resolution.
4. Use the selected Exa adapter for discovery and Firecrawl for selected-page extraction. If one provider already returns sufficient usable source content, reuse it without another paid call. Both providers overlap in features; selection does not require calling both for every question. Do not use recursive/deep crawling by default.
5. Store source URL, publisher, retrieval time, relevant excerpt, content hash, publication date when available, and freshness/verification status. A cached source can be reused only when its freshness policy allows it. Keep public-source records separate from confirmed user assertions.
6. Treat page content as untrusted source text, not instructions. Explain what came from Yama's records and what came from an external source. Official guidance needs official sources and applicable location/date checks; a search hit is not verified advice.

Initial limits to evaluate: one search and up to three selected pages per user goal; short timeouts, content-size caps, explicit failed/retry states, and application-enforced spend caps. If the limit is reached, continue from available sources or explain the gap; never imply a lookup succeeded. Further live-voice generation must keep obeying the speaking coordinator while web work runs.

Agent access should initially be **Drishti and Disha**. Saathi stays focused on intake and can delegate a permitted task. Common database/evidence capabilities remain scoped to the user's authorization. This tool policy must be implemented and tested before exposing a live web function.

## Free does not mean zero operating cost

Free SDKs still use laptop/server resources. Monthly allowances differ from one-time signup credits and new-account promotions. Budget OpenAI generation and embeddings as metered API usage; do not assume free trial credit. [OpenAI pricing](https://developers.openai.com/api/docs/pricing)

Sarvam's pricing currently lists ₹100 signup credit, STT ₹30/hour, and Bulbul v3 ₹30/10,000 characters; check the existing account balance rather than assuming it is unused. [Sarvam pricing](https://docs.sarvam.ai/api/getting-started/pricing)

Sarvam states that account-generated audio consuming signup credits can carry commercial production rights under its terms; no separate production tier is required for those outputs. This does not grant rights to the voices/models themselves. [Commercial licensing](https://docs.sarvam.ai/api/getting-started/commercial-licensing)

Keep provider auto-recharge/overages off at first and enforce Yama's own request/spend limits. Do not upgrade automatically when credits run out. Tests use fixtures. Provider accounts and real requests belong to deliberate integration checks; new paid subscriptions require the user's choice.

## Production decision still pending

The existing India-only requirement has not been relaxed. OpenAI's current documentation lists India regional storage, **not regional processing**; residency requires eligible data-control arrangements. Default API abuse monitoring and application-state retention also need explicit review: `store=false` does not by itself establish Zero Data Retention. OpenAI is selected for the synthetic demo; real-report processing remains unresolved until the user resolves this conflict. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)

Sarvam's selected **Model APIs** have configurable zero retention, while its managed **Voice Agents** product does not currently support zero days. Retain the Model APIs plus our LiveKit worker and explicitly configure retention before requests. [Sarvam retention](https://docs.sarvam.ai/api/platform/data-retention)

Hosted email, security, traces, web tools, and billing have their own processing and retention paths. A free tier is not approval for real reports. Preserve the existing public-launch safeguarding review and Dodo production eligibility/data-handling gate; public guidance lookup never authorizes disclosing a reporter's private account.
